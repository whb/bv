## 暂停预取"无缓存速度"根因（单位错误）
- 用户反馈：暂停只短时间显示"正在缓存"，无速度。
- 根因：`DataSpec.position/length` 单位是**字节**，而 `player.bufferedPosition/duration` 是**毫秒**。旧实现把毫秒当字节 → 只请求极小的错误字节区间 → `CacheWriter` 瞬间完成（0 字节或 <300ms）→ 速度永远算不出，只剩 1.2s latch 的"正在缓存"。
- 已用 javap 反编译 `media3-datasource-1.11.1.aar` 确认 `CacheWriter.ProgressListener.onProgress(long contentLength, long bytesCached, long newBytesCached)`，第 3 参是**每次读块的新增字节**；`cache()` 内部用 `getCachedLength` 跳过已缓存区间（幂等）。
- 修复（`ExoMediaPlayer.kt`）：新增 `loadedBytesByUri`，在 `AnalyticsListener.onLoadCompleted` 记录 `dataSpec.position + bytesLoaded` 作为各 URL 的真实字节前沿；`startPrefetch` 从该字节前沿预取到 EOF（`setLength(-1L)`），修正单位并贴合当前播放位置；单次预取上限 300MB（进度回调累计超限 `cacheWriter.cancel()`）；速度窗口内快速结束用总平均兜底。

## 缓存"边播边写"两个真 bug（2026-11-01 傍晚，提交 `efc0efbb`）
- **`CacheDataSource.Factory` 不设写槽 ≠ 只读**：media3 1.11 `createDataSourceInternal` 里 `cacheWriteDataSinkFactory == null` 会走 else 分支 `new CacheDataSink.Factory().setCache(cache)`，自动造写槽。真正的只读必须直接调 `CacheDataSource(cache, upstream, FileDataSource(), null /*cacheWriteDataSink*/, flags, null, CacheKeyFactory.DEFAULT)`。这是"播放就写盘/缓存目录一直涨/eMMC 写饱和"的真正根因，绕了三轮才定位（`javap -p -c CacheDataSource$Factory` 字节码可证）。
- **`CacheWriter.cancel()` 停不住预取**：`cache()` 只在"块"之间查 `isCanceled`，而预取 `DataSpec.length = -1`（读到末尾）⇒ 一整块就是整个剩余文件。修法：`CancellableDataSource(upstream, isCanceled)`（`BaseDataSource(true)` 子类，`read()` 前检查标志抛 IOException）包装预取上游，`cancelPrefetch()` 先置 `@Volatile prefetchCanceled = true`。
- 预取起点：`cache.getCachedSpans(url).filter{length>0}.maxOf{position+length}`（`cachedFrontier`）。原 `onLoadCompleted` 采集 URI 与 `lastVideoUrl` 匹配不上，日志里 8 次全是 `videoStart=0B`。
- **实测数据（ATV 模拟器）**：播放 21s 缓存恒定 20KB（仅 `.uid`，修复前同操作写 21MB）；暂停 8s 涨到 21.7MB；恢复播放 **1s 内**停止增长；二次暂停 `videoStart=22502956B`（接续末尾）；播放中 8s 内 eth0 rx 仅 632 字节、位置 01:00→02:19 ⇒ 播放确实走缓存文件。
- 注意：B 站播放地址带签名参数，跨会话 URL 变化 ⇒ cache key（默认 `uri.toString()`）变化 ⇒ 重进同一视频命中不了。因换片会清空缓存，目前无影响；若要跨会话复用需自定义 `CacheKeyFactory` 归一化。

## 暂停预取"谎报缓存完成"修复（2026-11-01 傍晚）
- **现象**：一个视频暂停缓存只落了 ~100MB（视频很少一部分）就显示"缓存完成"。
- **根因**：`ExoMediaPlayer.prefetchUrl()` 把 `writer.cache()` 的异常直接吞掉并 `return Done`。B 站签名 URL 过期、CDN 断流等会让预取中途抛异常，被忽略后误报"完成"；实际只有播放已缓存的 ~100MB 在盘上。
- **修复**：
  - `VideoPlayerCacheState` 新增 `Error`（缓存中断，部分可能已存；`visible` 仍 true）。
  - `prefetchUrl`：区分"取消"（恢复播放/跳转，`prefetchCanceled`+`IOException("prefetch canceled")`→ 由代次校验屏蔽）与"真实错误"；真实错误先有限重试（`PREFETCH_MAX_RETRIES=2`，退避 `PREFETCH_RETRY_BACKOFF_MS=1000ms`）绕过偶发断流，仍失败才 `return Error`；**"空间满"主动 cancel 触发的 IOException 必须判为 `Full`**（否则会被当错误处理/重试）。进度回调复用、跨重试累计计速。
  - UI：TV `PlayStateTips.CachingTip` 与 mobile `BvPlayerController.CachingTip` 的 `when` 新增 `Error -> "缓存中断"`（否则 `when` 非穷尽编译报错）。
- **附带**：构建时 `:player:shared:bundleLibCompileToJarDebug` 反复报 `classes.jar` 被占用——是上次构建残留的 Kotlin 编译守护进程（kotlin-compiler-embeddable）持锁，PowerShell `Stop-Process` 杀掉残留 java 后构建通过。
- 验证：`:app:assembleDefaultDebug` BUILD SUCCESSFUL（杀守护进程后）；`adb install -r` 成功；启动无崩溃。
- 待用户实测：暂停后提示应为"缓存完成"（真到 EOF）或"缓存中断"（诚实报错）；`adb logcat | Select-String ExoMediaPlayer` 可见重试/失败日志定位断流原因。

## TV 搜索框"系统键盘抢占、自定义键盘消失"修复（2026-11-01 傍晚）
- **现象**：进入 TV 搜索框后系统输入法弹出，app 自己的自定义软键盘（`SoftKeyboard.kt`）就没了。
- **根因**（`app/tv/.../screens/search/SearchInputScreen.kt` 的 `SearchInput`）：`OutlinedTextField` 获焦时 `LocalSoftwareKeyboardController.show()` 拉起系统 IME；同时 `if (!textFieldFocused)` 让自定义 `SoftKeyboard` 在输入框聚焦时被隐藏。TV 端本该只用自定义键盘（遥控器输入），系统 IME 既多余又抢焦点。
- **修复**：TV 搜索框改为"仅展示"——`OutlinedTextField` 加 `readOnly = true` + `Modifier.focusProperties { canFocus = false }`（脱离焦点链、永不请求系统 IME），并去掉 `if (!textFieldFocused)` 守卫使自定义键盘**始终显示**。删除 `keyboardController`/`textFieldFocused`/`onFocusEvent` 及 `KeyboardOptions`/`KeyboardActions`/`ImeAction` 等无用导入。所有输入一律走自定义键盘（`onSearchKeywordChange(searchKeyword + it)` 等）。
- 验证：`:app:assembleDefaultDebug`（JDK21）BUILD SUCCESSFUL。
- 注意：此修复仅针对 **TV** 搜索（`app/tv`）。mobile 搜索（`app/mobile/.../home/search/SearchInput.kt`、`component/home/SearchBar.kt`）本就用系统键盘，未改动；若 mobile 也有"自己的键盘"问题需另查。
