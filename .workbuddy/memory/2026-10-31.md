## 回退磁盘缓存（上一日优化的回归修复）
昨日提交的播放流畅度优化在 TV 盒子上出现回归：卡顿时 app 不响应操作、加载动画消失。

根因：新增的 `SimpleCache` 磁盘缓存在播放时把视频分片**实时写入 eMMC**，`SimpleCache` 每次写 span 都落库（fsync）。在雷鸟等低端 TV 上写放大/IO 饱和拖垮整个系统 → 视频卡顿 + 主线程掉帧（UI 不响应、Compose 加载动画一起冻住）。两症状同源（主线程被冻）。

`playUrl/prepare` 在 `Dispatchers.Main` 调用（`VideoPlayerV3ViewModel.kt:474`），但缓存 init 只在首播有一次，主因是持续写盘而非 init。

处理：删除 `BvMediaCache.kt`，`ExoMediaPlayer` 数据源改回直连 OkHttp（`dataSourceFactory`），回退 `media3-datasource`/`media3-database` 依赖。
保留：OkHttp 进程单例复用、轻量 `DefaultLoadControl`（60s/120s + prioritizeTimeOverSizeThresholds）、`setWakeMode(WAKE_MODE_NETWORK)`（均低风险且有益）。

校验：`:player:core:compileDebugKotlin --offline` 通过。

结论：TV eMMC 上**直播流实时落盘缓存弊大于利**（网络才是瓶颈，落盘是额外 IO）。若后续要缓存收益，应改为「仅 seek/回看命中、不写直播流」或更小/可开关的缓存，而非当前实现。

## 播放卡顿/错误时保证主线程（输入）优先级（player 内核，未提交）
用户要求：视频卡顿或出错时，处理用户输入的主线程优先级必须足够高（之前出过"卡顿时不响应操作"的回归）。

根因机制：ExoPlayer 默认 `playbackLooper` 绑定主线程（本工程在 `Dispatchers.Main` 上构造播放器），卡顿时播放器内部 buffer/track 消息挤占主线程消息队列，输入事件被排队 → 不响应。

方案取舍：曾考虑用 `ExoPlayer.Builder.setPlaybackLooper` 把播放线程移出主线程（最彻底），但本项目用 `PlayerView` 承载画面，media3 硬性要求 Surface 绑定必须在 `playbackLooper` 线程，移出主线程会导致 `setVideoSurfaceView` 抛 IllegalStateException 崩溃（高风险回归），故放弃。

最终做法（低风险、直接命中诉求）：在 `ExoMediaPlayer` 中——
- `initPlayer()` 末尾把主线程（UI/输入线程）调度优先级提升到 `Process.THREAD_PRIORITY_URGENT_DISPLAY`(-8)：高于普通后台(10)/默认(0)，保证卡顿/出错时输入优先被调度；但仍低于解码线程(AUDIO -16)，不饿死解码。
- `release()` 精确还原原始优先级（`savedMainThreadPriority`），消除全局副作用。
- 对 `onPlaybackStateChanged`/`onPlayerError` 等主线程回调加防御性约束注释：必须轻量，不得同步做网络/IO；若需错误后恢复/重试必须在 IO 线程异步。

补充：经排查，当前播放器 `onError` 各点（TV/mobile/BvPlayerPreview）仅 `logger`/`println` + 设 State，无同步阻塞重活（重试逻辑只存在于评论/列表刷新，与播放无关），本就满足轻量约束。

## 分析 error.log 崩溃 + 播放内核崩溃加固（未提交）
用户提供 `D:\error.log`（logcat）。结论：app **进程崩溃**而非仅冻结——
- `DropBoxManagerService: add tag=data_app_crash`（line 790）、`Zygote: Process 3997 exited due to signal 9 (Killed)`（801）、`Process ... has died`（820）。
- 时间线：13:18:39 启动 VideoPlayerV3Activity → 13:19:15 进程死亡（播放大码流约 36s 后）。
- 运行环境是**模拟器**（C2GoldfishAvcDec=软件 AVC 解码器），远弱于真实雷鸟 TV；codec 报错（806-814 `C2GoldfishAvcDec fetchGraphicBlock failed`/corrupted work）是进程死后的连锁反应，非根因。
- 关键：全日志**无 `AndroidRuntime: FATAL EXCEPTION` 行** → 要么栈被裁剪，要么崩溃发生在**非主线程**（无 `FATAL EXCEPTION: main`）。

据此加固三处潜在崩溃点（均编译通过，EXIT=0）：
1. `OkHttpUtil.CachingDns.lookup`：原仅 catch `UnknownHostException`；若在 OkHttp 调度线程抛出其他异常（SecurityException 等），会经 `KillApplicationHandler` 直接 SIGKILL 进程（data_app_crash 且无主线程 FATAL 行）——与本次日志吻合。改为 catch `Exception` 并回退过期缓存，无旧值才抛出。
2. `ExoMediaPlayer.prepare()`：原 `mMediaSource!!` 潜在 NPE，改为空守卫 `?: return`。
3. `ExoMediaPlayer` AV1 兜底回调 `onAv1DecodeFailed` 包 try/catch，避免上层 lambda 在主线程抛未捕获异常拖崩进程。

待办：仍未拿到真实崩溃栈（FATAL EXCEPTION 行），需用户用 `adb logcat -b crash` 或 `adb bugreport` 复现抓取确认根因；当前为防御性加固。另注意该崩溃可能仅为模拟器软件解码不稳，需在真实雷鸟 TV 复核。

### 最终根因锁定（bugreport.zip — 模拟器 tombstone/bugreport，21:55 续查）
用户提交 `D:\bugreport.zip`（ATV x86_64 模拟器，Android 16 `BT2A.260319.001`）。**翻案：不是 native 崩溃，也不是解码器导致，而是 Java OOM。**
- 关键行 `am_crash`：`java.lang.OutOfMemoryError, Failed to allocate a 8208 byte allocation ... growth limit 201326592 (192MB), Segment.kt,62` —— 崩溃点在 **Okio `Segment.kt:62`**（OkHttp 读网络数据时分配 8KB 缓冲），说明是**网络读取期间 Java 堆已耗尽**。
- 时间线：OOM(13:34:33.800) → `data_app_crash`(813) → Force finishing VideoPlayerV3Activity(821) → `C2GoldfishAvcDec fetchGraphicBlock failed status 22`(900) → `Zygote exited signal 9`(924)。**解码器报错与 SIGKILL 都是进程已死之后的收尾，非原因**（此前把因果判反了）。
- 直接诱因：上一轮给 `DefaultLoadControl` 设的 `setTargetBufferBytes(150MB)`。ExoPlayer 的样本缓冲（`DefaultAllocator`）分配在 **Java 堆**上；192MB 堆的设备上 150MB 缓冲直接 OOM，大码流持续缓冲即触发。SIGKILL 是 `KillApplicationHandler` 处理未捕获 OOM Error 的结果。
- zip 内**无 tombstone 文件**、logcat 也无 DEBUG 回溯：因为 OOM 不产生 tombstone；此前"需 adb logcat -b crash 取 tombstone"的方向作废。

### 修复（`ExoMediaPlayer.kt`，未提交）
- `TARGET_BUFFER_BYTES_CAP` 由硬编码 `150MB` 改为**基于堆上限动态计算**：`Runtime.maxMemory()*30/100`，封顶 80MB、保底 15MB。192MB 堆→约 57MB；512MB 堆→封顶 80MB。时间维度缓冲（MIN/MAX 60s/120s）保持不变，不损失平滑度；字节上限仅做内存兜底。
- 编译验证：`:player:core:compileDebugKotlin --offline` EXIT=0。
- 含义：此前误判的"模拟器软解不稳"实为内存爆掉；真机雷鸟 TV 若有同样 150MB 上限也会 OOM，故本次修复对真机同样有效。仍建议真机复核大码流长播。
