## UGC/PGC「部分加载失败」根因诊断
- 现象：进入 UGC（如 Kichiku 鬼畜）等分区，首次/翻页时部分列表弹"加载 X 数据失败"，logcat 出现 `I UgvViewModel[<类型>]: load more <类型> data failed: IllegalStateException: 暂时没有更多内容了`(乱码为 UTF-8 中文被 PowerShell GBK 误显)。
- 根因链：B站 `/x/web-interface/region/feed/rcmd` 在翻页到底/某些分区返回 `code!=0` + message「暂时没有更多内容了」→ `bili-api/.../http/entity/BiliResponse.kt:22` 的 `getResponseData()` 对 `code!=0`（非 -101/-352）统一 `throw IllegalStateException(message)` → `UgcViewModel.loadMore()` / `ZoneDetailViewModel.loadUgcRegionData()` 的 `runCatching.onFailure` 把它当作"加载失败"弹 toast。
- 本质：不是真错误，是"已到底/无更多"的正常终态被接口以非0 code 返回、被代码误判为加载失败 → 表现为"部分加载失败"。
- 失败日志去向：经 `fInfo` → (1) logcat INFO 级，tag=`UgvViewModel[类型]`(拼错少c)/`PgcViewModel[类型]`；(2) Firebase.crashlytics.log 面包屑(仅接入 google-services 时)；(3) 不自动落盘(仅崩溃/手动 logLogcat 才写 crash_logs/)。
- 修复方向（未执行，待用户确认）：在 UgcRepository.getRegionFeedRcmd 或 UgcViewModel 层把"没有更多"终态与真错误区分——message 含「没有更多内容」时设 hasMore=false 且不弹 toast；或 repository 返回空结果而非抛。注意 message 中文匹配脆弱，优先用接口返回的"是否到底"语义。

## 鬼畜分区编号 vs 官方文档核对（"鬼畜查不到视频"排查）
- 用户疑心 `region/feed/rcmd` 的 `from_region` 分区号写错。实测 + 对比官方 v2 分区表：
  - 官方 bilibili-API-collect `video_zone_v2`：鬼畜主分区 `tid=1007, channelId=9, code=kichiku`；子分区 guide=2059/theatre=2060/manual_vocaloid=2061/mad=2062/other=2063。
  - 项目 `UgcTypeV2.kt`：`Kichiku(1007,"kichiku",9)` 及 5 个子分区**与官方逐字一致**。
  - 老的 `UgcType.kt` 用 `rid=119`（旧 rid 系统，鬼畜主分区 rid=119，子分区 22/26/126/216/127），与旧 rid 系统也一致；但 `getRegionDynamic` 等已 `@Deprecated`，当前 `region/feed/rcmd` 走 `tid`。
- **实测（WebFetch 直接打线上接口）**：
  - `from_region=1007&display_id=1&request_cnt=15&device=web&plat=30` → `code:0`，返回 15 条真实鬼畜视频 + banner 6 条 ✅
  - `from_region=119` → `code:-400 请求错误, data:null` ❌
  - 即 `tid=1007` 正确，`rid=119` 才是错的（反证项目用 tid 是对的）。
- **结论**：编号无误，鬼畜"查不到视频"不是分区号问题。真正原因更可能是：① B站服务端地域限制（本项目原为非大陆设计，从大陆网络访问 `region/feed/rcmd` 等可能被返回空/错误码，区别于已摘除的启动期 Cloudflare 大陆拦截）；② 设备网络连不上 api.bilibili.com；③ 翻页到底的"暂时没有更多内容了"误报（见上）。需抓 app 实际收到的 `code/message` 才能定位。`getResponseData()` 把非0 code 一律转异常，首次加载若拿到 -404/-412 等会被当作"失败"而非"地域限制"。
- 下一步建议：在 `loadUgcRegionData`/`getResponseData` 失败处把真实 code/message 透出到 toast/日志，区分「地域限制 / 到底 / 网络 / 真错误」。

## PGC 栏目轮播图加载特别慢 —— 根因+修复（仅改文件未编译）
- 现象：PGC（电影/番剧/纪录片等）分区顶部轮播图加载很慢。
- 根因：`bili-api/.../entity/CarouselData.kt` 的 `fromPgcWebInitialStateData` 优先取 `it.bigCover ?: it.cover`——`bigCover` 是 B 站画廊原图画廊大图（常 1920×600+ 且为 png/jpg），直接喂给 `CarouselCard` 的 `AsyncImage(model = data.cover)`。而番剧卡片封面都走了 `resizedImageUrl(ImageSize.SeasonCoverThumbnail)` 生成 `@尺寸.webp` 缩略图，PGC 轮播却没做这一步 → 拉原图 → 慢。
- 修复：`fromPgcWebInitialStateData` 在确定 `cover` 后，对 hdslb bfs 域名的 URL 追加 CDN 动态缩放后缀 `@480h.webp`（`if (cover.contains("hdslb.com/bfs")) cover = "$cover@480h.webp"`）。轮播高 240dp（移动/TV 常见密度约 480px），@480h 足够清晰且体积大幅缩小；转 webp 是主要加速点。
- 安全性：缩放后缀仅对 `hdslb.com/bfs` 域名生效，其它域名（异常/外部图）走原 URL，不破坏；B 站 CDN 动态缩放已验证返回 `image/webp`（用 tech banner 图 `...png@480h.webp` 实测 Content-Type=image/webp）。
- 影响面：修复在 `bili-api` 数据层，TV(`PgcCarousel`/`CarouselCard`) 与 mobile 两端 PGC 轮播共用同一 `PgcRepository.getCarousel`，均受益。UGC 轮播未改动（其 cover 来自 region banner，非 bigCover）。
- 验证：仅改文件，未跑 gradle（沙箱网络受限）。建议本地 `./gradlew :app:tv:assembleLiteDebug` 验证 PGC 轮播秒出图。

## UGC 全分区 NPE：getRegionFeedRcmd on a null object（已修复并编译通过）
- 现象：进入任意 UGC 分区（Dance/Cinephile/Ent/Knowledge/Ai/Home…）首屏即 `java.lang.NullPointerException: Attempt to invoke virtual method '...UgcRepository.getRegionFeedRcmd(...)' on a null object reference`，`UgcViewModel.loadUgcRegionData(UgcViewModel.kt:67)` 全程被包在 `runCatching` 里只弹 toast、不崩进程，但数据永远加载不出来。
- 根因（非 Koin 注入问题）：Kotlin **构造期属性初始化顺序陷阱**。`UgcViewModel` 把 `ugcRepository` 声明为 `open val`，47 个子类用 `override val ugcRepository` 重写。`init` 块里 `viewModelScope.launch(Dispatchers.IO){ initUgcRegionData() }` 在父类构造函数阶段就跑，此时子类 `override` 字段尚未赋值 → 读到 `null`。`ugcType` 是普通 `val` 故不受影响，唯独 `ugcRepository` 全 null —— 与"所有分区稳定 null"特征吻合。
- 修复：去掉 open/override，使 `ugcRepository` 成为父类唯一、构造期即赋值的 `val`：
  - `app/shared/.../viewmodel/ugc/UgcViewModel.kt`：`open val ugcRepository` → `val ugcRepository`。
  - 47 个子类 `Ugc*ViewModel.kt`：`override val ugcRepository: UgcRepository` → `ugcRepository: UgcRepository`（去掉 override，仅作构造参数传给父类）。`ZoneDetailViewModel`/`UgcScaffoldState` 用的是各自 `private val ugcRepository`，模式不匹配、未动。
- 验证：`:app:shared:compileDebugKotlin` + `:app:tv:compileDebugKotlin` + `:app:mobile:compileDebugKotlin` → **BUILD SUCCESSFUL**。KSP 的 `default value injection skipped`/`defaultModule deprecated` 为无关 warning。
- 备注：这是对象构造期访问 open/override 属性的经典坑；今后在 `init`/构造期访问的属性不要用 `open val`+`override val`。

## 雷鸟85S545C(MTK9652) 能否 4K60 AV1 硬解 —— 代码+硬件核查
- 用户问：代码能否用硬解压最高 4K60 AV1。
- 硬件：MTK9652 SoC 规格明确支持 AV1 解码（解码列表含 AV1/AVS2/HEVC/VP9/H.264/SHVC，4K60@10bit，最大刷新率120Hz）；雷鸟85S545C 即 MTK9652。硅片能力足够 4K60 AV1 硬解。
- 代码播放引擎真相（纠正旧记忆）：TV/mobile 播放实际用 **Media3 / ExoPlayer**（`ExoPlayerFactory`→`ExoMediaPlayer`，`DefaultRenderersFactory`），**不是** libVLC（VLC 的 .so 虽在但播放未走它）。ExoPlayer 默认用 MediaCodec 硬件解码器，只要是系统 MediaCodec 暴露的解码器就会自动选用，AV1 无硬编码屏蔽。
- AV1 支持：`player/shared/.../entity/VideoCodec.kt` 枚举含 `AV1("av01",13)` 且映射到 B站 `CodeType.CodeAv1`，说明代码能请求并播放 AV1 流。
- 唯一变数=电视固件是否通过 MediaCodec 暴露 AV1 硬件解码器（`c2.mtk.av1.decoder` 之类）。若暴露，ExoPlayer 自动硬解 4K60；若只暴露软解，A73 四核 4K60 软解会卡。
- 自带验证入口：TV App → 设置 → 关于 → MediaCodec（`MediaCodecActivity`/`MediaCodecScreen`，底层 `CodecUtil.parseCodecs()` 枚举全部 decoder，含 mimeType/硬软(mode)/分辨率帧率）。找 `mimeType=video/av01.0` 且 mode=Hardware、支持 2160p@60 即可确认。
- 结论：设备能、代码能；最终能否 4K60 硬解取决于雷鸟85S545C 固件是否开放 AV1 硬件解码器，需在电视上用上述页面或 `adb shell dumpsys media.codec | findstr av01` 实测确认。

## 「设置→关于→MediaCodec」点进去直接退回首页（崩溃）修复
- 现象：TV App 进入 设置→关于→解码器信息，不显示解码器、瞬间回到 TV 主界面（首页）。
- 根因：MediaCodecActivity 是叠在 TV 主 Activity 之上的独立 Activity；其 `MediaCodecScreen` 在 `LaunchedEffect` 里调 `CodecUtil.parseCodecs()`，而 `fromCodecInfo` 写 `codecInfo.getCapabilitiesForType(codecInfo.supportedTypes.first())` 未做容错——个别厂商 codec（如空 supportedTypes、或 getCapabilitiesForType 抛 IllegalArgumentException）会导致**单条解析抛异常 → 整个 parseCodecs 抛异常 → Activity 崩溃被系统销毁 → 退回首页**。`MediaCodecScreen` 还有 `list[0]` 空列表越界风险。
- 修复（`CodecUtil.kt` + `MediaCodecScreen.kt`，已 `:app:assembleDefaultDebug` BUILD SUCCESSFUL）：
  - `parseCodecs()` 改为 `.mapNotNull { runCatching { fromCodecInfo(it) }.getOrNull() }`（单条失败跳过，不影响整体）。
  - `fromCodecInfo` 返回 `CodecInfoData?`：`supportedTypes.firstOrNull()` 空则返 null；`getCapabilitiesForType` 与 `colorFormats` 用 `runCatching` 包裹。
  - `MediaCodecScreen` 删掉只 println 的重复 `LaunchedEffect`；`list[0]` → `list.firstOrNull()`（空则显示 Empty）。
- 验证建议：重装 debug 包后，雷鸟上该页面应能正常列出解码器（含 `video/av01.0`）。另：AV1 硬解是否暴露仍需在该页确认 `video/av01.0` 且 mode=Hardware。
